  ▎ ★ Insight ─────────────────────────────────────
  ▎ drop_params is litellm's portability lever: you send one superset of params 
  ▎ and it strips whatever the target provider rejects. But note the asymmetry 
  ▎ it papers over — Gemini enforces the schema server-side (responseJsonSchema 
  ▎ + enforce_validation), whereas Ollama only gets plain JSON mode, so a small 
  ▎ local model isn't constrained to your schema, just nudged by the 
  ▎ SYSTEM_PROMPT's "return valid JSON matching the schema." That makes 
  ▎ PatientLabels.model_validate_json(...) the common validation floor across 
  ▎ providers — and you should expect a small gemma3 to fail that validation 
  ▎ more often than Gemini did. That's exactly the experiment: can a local model
  ▎ produce schema-valid output well enough to dodge the quota?

  The actual compatibility blocker (why gemma4 invented fields)

  Ollama can do near‑100% schema adherence — but only when the schema is passed
  as response_format={"type": "json_schema", "json_schema": {...}} (constrains
  inference). Our call uses Gemini's {"type": "json_object", "response_schema": 
  …}, and with drop_params=True Ollama just gets basic JSON mode — not
  schema‑constrained. So the model free-forms its own fields, and only
  enforce_validation catches it afterward. Even Qwen3 will do this until
  extract() sends Ollama the json_schema form.

  ▎ ★ Insight ─────────────────────────────────────
  ▎ So the gemma4 failure was two problems stacked: a weak small model and an 
  ▎ unconstrained call. A bigger model (Qwen3) fixes the first; provider-aware 
  ▎ response_format fixes the second. The second matters more — without 
  ▎ schema-constrained decoding, you're relying on prompt-adherence, which is 
  ▎ exactly what small local models are worst at. The clean fix is to branch 
  ▎ response_format on model.startswith("ollama") → Ollama gets json_schema, 
  ▎ Gemini keeps response_schema.
  ▎ ─────────────────────────────────────────────────
